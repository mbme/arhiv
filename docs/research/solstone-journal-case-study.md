# Solstone Journal and Arhiv: from captured evidence to committed knowledge

Solstone Journal is a useful reference for making personal activity searchable and usable by agents. Arhiv solves a different problem: keeping structured records that the owner has chosen to commit, with revision history and encrypted storage. The opportunity is to let automation make a captured item easier to find and file, while leaving the decision about what belongs in the archive to the owner.

This case study applies the distinctions in [Lifestreams](modern-lifestream-research-report.md) and [Personal Information Management Beyond Lifestreams](pim-beyond-lifestream-research-report.md) to a concrete system. It is based on pinned upstream documentation and its published fixture example, plus Arhiv's local contracts and CLI source. Neither system was run. The recommendations are exploratory, not roadmap commitments.

## One meeting, two jobs

Suppose you want to find out who agreed to check a project's migration plan, then keep a record of the decision.

**Solstone helps recover the episode.** Audio shared from a paired app or imported as a file enters a journal on an owner-controlled host. The journal stores dated segments, transcribes audio, attributes speakers, and processes captured material into outputs such as activities and entity connections. In the [upstream fixture example][solstone-agents], a connection between Romeo and Mercutio is backed by both a named meeting and a dated conversation segment. Those references give the reader somewhere to check the claim rather than asking them to trust the graph alone. The example shows what retrieval returns, not how accurate it is on real meetings. See also the [upstream architecture][solstone-architecture].

**Arhiv helps keep the decision.** The owner can write a record, link it to existing documents where the schema permits, stage it, and commit it. Later, the owner can inspect retained revisions or reconcile competing edits from different devices. Arhiv is not inferring what happened in the meeting; it records what the owner decided to retain. See the [domain model](../domain-model.md) and [merge contract](../specs/merge-conflicts.md).

The useful distinction is between **captured evidence** (the audio), **derived material** (the transcript and an inferred commitment), and **an owner-approved record** (the decision as filed). A transcript can be wrong even when the audio is intact. An approved record can outlive the evidence that informed it without pretending the evidence is still available.

## Tradeoffs that matter to Arhiv

| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| What does the system keep?      | Journal files contain both inputs and processed outputs. SQLite full-text search is a rebuildable index, not the canonical store. See the [on-disk layout][solstone-disk].                                                                                                                                                          | Committed snapshots and asset blobs are durable storage. The local index and staging live separately from synchronized committed storage. See [architecture](../architecture.md).                                                                      |
| Who controls corrections?       | MCP `suggest_correction` queues proposals about visible material, such as speaker attribution. The owner can accept or dismiss them; acceptance records who suggested the correction. This is a review workflow, not a general edit API. See [Agent suggestions][solstone-mcp].                                                     | The owner can stage, inspect, and commit edits. A staged merge doesn't resolve competing revisions until it is committed. See the [domain model](../domain-model.md).                                                                                  |
| Where do devices do their work? | Paired apps feed a journal host that processes, indexes, and serves the material. See the [upstream architecture][solstone-architecture].                                                                                                                                                                                           | Devices can edit local copies independently. External file sync delivers encrypted committed storage; Arhiv handles concurrent document revisions. See [architecture](../architecture.md).                                                             |
| What does “private” cover?      | The docs describe a directly readable live journal and separately describe encrypted backups. The bundled local model keeps model requests on the host; configured external processing can receive task-specific content. See the [on-disk layout][solstone-disk], [backup CLI][solstone-cli], and [data flow][solstone-data-flow]. | Arhiv encrypts document data and asset blobs at rest with age. Filesystem metadata remains visible, and encryption does not protect plaintext from a compromised unlocked runtime. See the [system threat model](../system-threat-model.md).           |
| What can an agent access?       | The CLI and MCP support retrieval such as search, transcripts, and entity lookups. MCP separates journal reads, a connection's own memory, and correction suggestions. See [agent access][solstone-agents] and [MCP authorization][solstone-mcp].                                                                                   | The CLI already supports JSON search and document reads. JSON is an output format, not an access boundary. A dedicated agent CLI and skill remain [backlog ideas](../../BACKLOG.md). See the [CLI declarations](../../arhiv-cli/src/bin/arhiv/cli.rs). |

Solstone's host topology makes sense for coordinating capture and processing. Arhiv's replica model makes sense for independently editable archives. Borrowing the capture-to-retrieval workflow does not require adopting the host topology or moving the archive out of encrypted storage.

## Recommendations for Arhiv

1. **Start with retrieval, using what exists.** Try `arhiv search --json` and `arhiv get --json` on a disposable archive. See whether an assistant can find and cite the right record with only the fields and documents needed for the task. Define the intended read scope before giving an agent credentials or shell access to a real archive; limiting what the prompt asks for does not enforce access.
2. **Try one capture-to-suggestion workflow.** Give the assistant one manually captured meeting note and ask it to draft a record or suggest a link to an existing project. Show the supporting passage next to the suggestion and distinguish what the note says from what the model inferred. Let the owner edit or discard the suggestion, or explicitly stage and commit it. Arhiv commits the whole staging set, so keep this experiment from committing unrelated staged work.
3. **Measure review effort, not capture volume.** Compare the assisted flow with filing the same kind of note manually. Can the owner verify it quickly, catch a wrong project or speaker, and keep only the useful result? If review and cleanup cost more than manual filing, stop there. Continuous capture, automatic commits, and a journal-host redesign are outside this experiment.

Retention is a separate decision. Keeping a decision need not mean keeping the recording forever. Deleting a recording also need not erase its excerpts from summaries, indexes, exports, or backups. Before trying automated capture or expiry, decide which copies should survive and how to present a source that is no longer available.

## Evidence gaps and follow-up

The fixture example shows evidence references in retrieval results, and the MCP contract describes owner review of certain corrections. Neither establishes how a specific inferred relationship changes after correction or what happens to it when the source segment is deleted. A useful follow-up would trace one fixture connection from the lookup result to its stored evidence, then check what changes after an applicable correction and after source removal. Check the journal files, derived outputs, and search results separately. This study does not establish processing quality, performance, or runtime security.
